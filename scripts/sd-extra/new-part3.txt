@new part-3 h4 design-typeahead-search-autocomplete |  | Design Typeahead / Search Autocomplete
P: As a user types "sys", the box must show the five or ten most useful completions (for example "system design", "sysco") within about 100 ms, on every keystroke. ==It is a read-heavy, latency-critical problem on slowly changing data, so the answer is precomputation: build the suggestions offline and serve them from memory.==
H: Requirements
- Return the top 5 to 10 completions for any prefix, ranked by popularity (and optionally personalised).
- p99 latency under 100 ms; the browser sends a request per keystroke, so traffic is a multiple of search traffic.
- Trending queries should appear within minutes or hours, not days. Offensive terms must be filtered.
H: Back-of-the-envelope
P: 10 million daily users x 10 searches x about 5 keystrokes is roughly 500 million suggestion requests a day, around 6,000 per second on average and perhaps 20,000 at peak. The suggestion data itself is small (hundreds of millions of popular queries), so it fits in memory across a few machines.
H: Architecture
MERMAID:
flowchart LR
  B["Browser (debounced)"] --> E["CDN / edge cache"]
  E --> G["API gateway"]
  G --> S["Suggestion service (in-memory trie shards)"]
  L["Search query logs"] --> K["Kafka"]
  K --> A["Aggregation job (counts per query)"]
  A --> T["Trie builder"]
  T --> O["Snapshot in object storage"]
  O --> S
END
H: The key idea: a trie with the top results stored at every node
P: A **trie** is a tree where each step spells one more character. - A batch job counts queries from the logs (hourly or daily) and rebuilds the trie, then servers load the new snapshot and swap it in atomically.
- A small "trending" structure, updated every few minutes from a stream, is merged into results so breaking news appears quickly.
- Shard by prefix range or by hash of the first characters; replicate each shard for availability.
H: Making it feel instant on the client
- **Debounce** keystrokes (wait about 100 to 150 ms), **cancel** stale requests, and **cache** results per prefix in the browser.
- Short, common prefixes are cached at the CDN; personalised suggestions are blended in on the client or at the gateway.
H: Trade-offs and follow-ups
- Freshness versus cost: rebuilding more often is more expensive. Typo tolerance (fuzzy match) multiplies lookup cost, so apply it only when exact results are few.
- Safety: filter harmful or private completions before they enter the trie.
- Ranking beyond raw counts: recency, locale and personal history.

@new part-3 h4 design-dropbox-google-drive-file-sync |  | Design Dropbox / Google Drive (File Storage and Sync)
P: Users keep files in the cloud and see them on every device, share them, and recover old versions. ==The central trick is to cut every file into chunks, identify each chunk by its hash, and transfer only the chunks that are new or changed.== That saves bandwidth, makes uploads resumable and lets identical chunks be stored once.
H: Requirements
- Upload, download, share and keep devices in sync, including large files and flaky connections.
- Version history and conflict handling when two devices edit the same file offline.
- Fast sync of small edits to big files; strong durability.
H: Architecture
MERMAID:
flowchart LR
  C["Client (watcher + chunker)"] --> M["Metadata service (database)"]
  C --> B["Block store (object storage)"]
  M --> N["Notification service"]
  N --> C2["Other devices"]
  C2 --> M
  C2 --> B
END
H: How a sync works
1. The client notices a changed file and splits it into chunks (for example 4 MB), computing a hash for each.
2. It asks the metadata service which hashes are missing; chunks that already exist (even from another user) are skipped.
3. It uploads only the missing chunks to the block store, in parallel and resumably.
4. It commits a new file version in the metadata service: an ordered list of chunk hashes.
5. The notification service tells the other devices; they fetch the new metadata and download only the chunks they lack.
H: Ideas worth explaining
- **Content-defined chunking** uses a rolling hash to place chunk boundaries based on content, so inserting a few bytes at the start of a file changes one chunk instead of shifting all of them.
- **Deduplication**: identical hashes are stored once. Across users it saves space but can leak whether a file exists, so some products dedupe only within an account.
- **Metadata vs data**: file trees, versions and permissions live in a sharded database; bytes live in object storage. They scale independently.
- **Conflicts**: if both sides changed a file while apart, keep both ("conflicted copy") instead of silently overwriting.
H: Trade-offs and follow-ups
- Chunk size: small chunks dedupe and resume better but add metadata overhead.
- End-to-end encryption prevents server-side search and cross-user dedupe.
- Sharing links, permissions inheritance and real-time notifications at scale (long-lived connections).

flowchart LR
  A["Participant A"] -->|"RTP over UDP"| S["SFU media server"]

  G -.-> S
  S --> R["Recorder"]

@new part-3 h4 design-a-full-text-search-system-elasticsearch-style |  | Design a Full-Text Search System (Elasticsearch-style)
P: Users type words and expect the most relevant documents out of billions, in milliseconds. ==Search engines do not scan documents; they keep an inverted index that maps every word to the list of documents containing it.== The index is derived data, so the primary database stays the source of truth.
H: Requirements
- Index billions of documents; keyword queries with relevance ranking, filters and facets.
- Near-real-time: a new document is searchable within seconds.
- Horizontally scalable and highly available; reindexing without downtime.
H: Architecture
MERMAID:
flowchart LR
  D["Source database"] --> K["Change stream (Kafka)"]
  K --> I["Indexer workers"]
  I --> S1["Shard 1 (primary + replica)"]
  I --> S2["Shard 2 (primary + replica)"]
  Q["Query"] --> C["Coordinator node"]
  C --> S1
  C --> S2
  C --> R["Merge top-K and return"]
END
H: How indexing works
1. **Analysis**: split text into tokens, lowercase, remove stop words, reduce words to stems ("running" becomes "run").
2. Each term gets a **postings list**: the documents (and positions) where it occurs.

- The coordinator sends the query to every shard (scatter), each shard returns its best K matches, and the coordinator merges them (gather).

- Shard count: too few limits scale, too many tiny shards waste overhead. Documents are placed by hash of ID.
- Deep pagination is expensive; use a "search after" cursor instead of large offsets.
- Search is eventually consistent with the database; keep the ability to rebuild the index from the source.
- Relevance tuning (synonyms, boosts, personalisation) is where most real effort goes.

@new part-3 h4 design-a-distributed-lock-service |  | Design a Distributed Lock Service
P: Sometimes only one worker may do something at a time: run a scheduled job, update a shared resource, act as leader. A lock service hands out that exclusivity across many machines. ==The hard part is not taking the lock; it is surviving crashes, pauses and network splits without two holders ever believing they own it.==
H: Requirements
- Mutual exclusion: at most one holder at a time.
- No permanent deadlock if a holder crashes (locks expire).
- Highly available, with waiting clients notified when the lock frees.
H: Architecture
MERMAID:
flowchart LR
  C1["Client 1"] --> L["Lock cluster (Raft: etcd / ZooKeeper)"]
  C2["Client 2"] --> L
  C1 -->|"request + fencing token"| R["Protected resource"]
  R -->|"rejects lower token"| C2
END
H: Building blocks
- A small **consensus cluster** (three or five nodes running Raft or ZAB) stores lock state, so a majority agreement decides who holds the lock.
- A lock is a **lease**: the holder keeps it alive with heartbeats; if they stop, the lease expires and the lock is released.
- Waiters **watch** the lock key and are notified when it is released, instead of polling.
H: The trap: pauses and fencing tokens
P: A holder can freeze (a long garbage-collection pause, a stalled VM), its lease expires, another client takes the lock, and then the first one wakes up still believing it holds it. Both write. The fix is a **fencing token**: each grant carries a number that always increases, the client sends it with every write, and the protected resource rejects any request with a token lower than one it has already seen.
H: Redis-based locks
- A single Redis `SET key value NX PX ttl` is simple and fast, and fine when occasional double execution is harmless.
- It does not give the strict guarantee above, because of failover and clock or pause issues. When correctness matters, use a consensus-backed store and fencing tokens.
H: Trade-offs and follow-ups
- Prefer not needing a lock: idempotent operations or optimistic concurrency (version checks) avoid the problem altogether.
- Keep critical sections short and set lease times longer than normal pauses, but not so long that recovery is slow.

- Window size versus freshness; storage cost of raw data versus the ability to reprocess.

@new part-3 h4 design-a-digital-wallet-ledger |  | Design a Digital Wallet and Ledger
P: A wallet holds balances and moves money between users. ==Two rules are non-negotiable: a balance can never go negative by a race, and the same transfer can never be applied twice.== Everything else, including audit and reconciliation, follows from storing money as an immutable ledger.
H: Requirements
- Add money, withdraw and transfer between wallets; strong consistency for balances.
- Idempotent API, full audit trail, no lost or duplicated transfers.
- Handle hot accounts (a big merchant receiving thousands of payments per second).
H: Architecture
MERMAID:
flowchart LR
  C["Client"] --> W["Wallet API (idempotency key)"]
  W --> TX["Transfer service"]
  TX --> L["Ledger database (double entry)"]
  TX --> EV["Event stream"]
  EV --> N["Notifications"]
  EV --> RC["Reconciliation"]
  RC --> BK["Bank / PSP files"]
END
H: How a transfer works
1. The client sends the transfer with an **idempotency key**; a repeat returns the first result.
2. In **one database transaction**: check the sender's balance, write a debit entry and a credit entry, and update both balances. Either all of it happens or none of it.
3. Concurrency is controlled with row locks or a version check, so two simultaneous transfers cannot both spend the same money.
4. An event is published for notifications and analytics.
H: Ideas worth explaining
- **Double-entry ledger**: every movement is a debit and an equal credit in append-only rows. Corrections are new entries, so history is never rewritten.
- **Same shard or not**: if both wallets live in one shard, a local transaction is enough. Across shards use a **saga** (debit, then credit, with a compensating refund on failure) or two-phase commit.
- **Hot accounts**: split a busy merchant balance into several sub-balances that are summed on read, so writes do not all contend on one row.
- **Money as integers**: store minor units (cents), never floating point.
H: Trade-offs and follow-ups
- Strong consistency limits write scale per account; shard by account and keep a transfer within one shard when possible.
- Limits, fraud checks and regulatory reporting run asynchronously from the event stream.

@new part-3 h4 design-a-content-delivery-network-cdn |  | Design a Content Delivery Network (CDN)
P: A CDN keeps copies of content in many cities so users fetch it from a nearby server instead of the faraway origin. ==Its job is to cut latency and shield the origin, and its success is measured by the cache hit ratio.==
H: Requirements
- Serve static (and cacheable dynamic) content with low latency worldwide.
- High hit ratio, quick purge of changed content, TLS, and protection against traffic floods.
H: Architecture
MERMAID:
flowchart LR
  U["User"] -->|"DNS or anycast"| E["Edge PoP cache"]
  E -->|"miss"| M["Regional mid-tier cache"]
  M -->|"miss"| SH["Origin shield"]
  SH -->|"miss"| OR["Origin servers"]
  OR --> SH --> M --> E --> U
END
H: Routing users to the right place
- **GeoDNS** answers with the address of the nearest healthy point of presence, based on the resolver's location and server load.
- **Anycast** announces the same IP from every location, and internet routing sends each user to the closest one, which also spreads DDoS traffic.
H: Caching rules
- The origin controls freshness with `Cache-Control` headers (how long to keep a copy). Expired copies are **revalidated** with `ETag` or `If-Modified-Since`, so unchanged files are not downloaded again.
- The **cache key** says what makes two requests the same (URL, selected headers, device class); a sloppy key fragments the cache.
- **Purge** requests must reach every location quickly; versioned file names (`app.3f9a.js`) avoid the need to purge at all.
H: Protecting the origin
- **Tiered caching**: edge misses go to a regional cache and then a single origin shield, so the origin sees only a trickle.
- **Request collapsing**: if a thousand users ask for the same missing file at once, only one request goes upstream and the rest wait for it.
- Inside a PoP, **consistent hashing** spreads files across servers so each file is stored once.
H: Trade-offs and follow-ups
- Longer TTLs raise hit ratio but serve staler content.
- Dynamic content can still benefit from persistent connections and TCP/TLS termination near the user.
- Security: TLS certificates at the edge, signed URLs for private content, and bot and DDoS filtering.
