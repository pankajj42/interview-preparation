Part IV — Cheat Sheets

Quick-reference tables, meant to be scanned in the minutes before an interview, not read start to end.

4.1The framework, one more time

Step Ask yourself
Requirements Functional? Non-functional? Scale? What's explicitly out of scope?
Estimation QPS, storage/year, bandwidth — three numbers, out loud
High-level design Boxes and arrows: client → gateway → services → data layer
Deep dive Whatever the interviewer leans toward — usually data model or the one hard trade-off
Wrap-up Bottlenecks, SPOFs, what you'd add with more time

4.2SQL vs. NoSQL at a glance

Signal in the requirements Lean toward
"Must never lose a transaction" / financial ledger SQL (ACID)
Schema will change often, nested data Document NoSQL
Simple lookup at extreme write volume Key-value or wide-column
"How are these entities connected" is the core query Graph
Full-text/fuzzy search Text-search (Elasticsearch)
Time-stamped sensor/metric data Time-series

4.3Load balancing algorithms

Algorithm One-line pick
Round robin Uniform servers, uniform requests
Weighted round robin Servers of different sizes
Least connections Requests of wildly different duration
Consistent hash Need session stickiness or cache-affinity
Least bandwidth Streaming/bandwidth-heavy traffic

4.4Caching strategies

Need Strategy
Simple, resilient to cache failure Cache-aside
Cache must never look stale after a write Write-through
Writes must be fast, some loss risk tolerable Write-behind
Full data set, hands-off population Read-through
Cache full, pick what to evict LRU (default) or LFU (stable popularity)

4.5Rate limiting algorithms

Need Algorithm
Simple, low-stakes Fixed window
Strict precision Sliding window log
Scalable public API default Sliding window counter or token bucket
Must smooth output to a constant rate Leaky bucket

4.6Consensus & coordination

Need Reach for
Leader election / distributed locks / config ZooKeeper, etcd, Consul
Understandable replicated log implementation Raft
Historically foundational reference Paxos

4.7CAP in practice

System Choice under partition
Traditional single-node RDBMS CA (no partition to tolerate)
MongoDB (default config) CP — rejects writes it can't safely replicate
Cassandra, DynamoDB AP — answers with best-available data
DNS AP — a stale answer beats no answer

4.8Sharding strategies

Need Strategy
Even distribution, can tolerate resharding cost Key/hash-based
Efficient range queries Range-based
Maximum rebalancing flexibility Directory-based
Isolate hot/critical columns Vertical
Minimize reshuffling on resize Consistent hashing (on top of hash-based)

4.9"If the question needs X, reach for Y"

The requirement says... Reach for
"Real-time, bidirectional" WebSocket
"Stream updates to the client, one direction" Server-Sent Events
"Exactly-once side effects despite retries" Idempotency key + dedupe table
"Multiple services, one atomic-feeling operation" Saga (choreography or orchestration)
"Full audit trail / time travel" Event sourcing
"Reads and writes have wildly different load" CQRS
"Protect a downstream dependency from cascading failure" Circuit breaker
"Find things near a location" Geohash / Quadtree / H3
"Dedupe URLs across a huge, uncertain set" Bloom filter
"One writer, many readers, minimize reshuffle on scale change" Consistent hashing
"Ground an LLM's answer in our own data" RAG + vector DB
"Update the DB and publish an event, atomically" Outbox pattern (+ CDC to relay it)
"A lock must stay safe even if the holder pauses past its TTL" Fencing tokens
"One key/record is getting way more traffic than the rest" Key salting + local cache + single-flight (the hot-key toolkit)
"Many cache entries expiring at once is hammering the DB" Jittered TTLs (cache avalanche fix)
"Approximate unique-count over a huge stream, memory-constrained" HyperLogLog
"One slow dependency shouldn't exhaust resources shared with others" Bulkhead (isolated pools per dependency)
"A counter is getting hammered by concurrent writes" Sharded counters, summed on read

4.10Numbers worth having memorized

Fact Value
99.9% uptime allows ~8.7 hours downtime/year
99.99% uptime allows ~52 minutes downtime/year
99.999% uptime allows ~5 minutes downtime/year
Seconds in a day / month / year ~86,400 / ~2.6M / ~31.5M
Memory vs. cross-continent network round trip Memory is roughly 1,000,000× faster
A well-tuned single relational DB, rough QPS ceiling Low tens of thousands before sharding conversations start
